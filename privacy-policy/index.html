1. About this policy

This policy explains how Surah Al Baqarah – OFFLINE (the “app”) handles information when you use its features. The developer identified above is responsible for the app. Google's services and websites linked below also have their own privacy terms.

Core features work without an internet connection: bundled Surah Al-Baqarah audio, bundled Quran reading, bookmarks, Tasbih, available local daily content, prayer calculations and local prayer reminders. Location detection and delivery of reminders depend on device services, settings and permissions. Not all planned daily content or language editions are currently available.

Offline functionality does not mean that no information is collected, processed or shared. Device storage, optional permissions, service SDKs and online interactions are described below.

2. Information used for offline features

The app does not require an account in the inspected version. It stores information in private app storage to provide and restore your experience, including:

  • Language, appearance and reader preferences; reading progress and bookmarks.
  • Audio playback position and repeat preferences.
  • Tasbih counts and session history, and available daily-content progress.
  • Prayer coordinates, timezone and calculation preferences; notification and reminder schedules.
  • Bundled content copies and installed language-pack files, where available.

These records support the corresponding local features. The inspected application code does not send these records to a developer-operated server or deliberately pass them to advertising or Firebase services. Reading, worship and location records can be sensitive; this statement must be rechecked if integrations change.

3. Location and notifications

Location is optional. You can enter prayer coordinates manually. If you select “Use device location,” the app requests Android location permission and obtains coordinates through Android's foreground location services to calculate prayer times on the device. Approximate or precise location depends on your permission choice and device support. The app does not request background location or send coordinates to an online prayer-time service. Android's location provider may itself use network services according to your device settings and its provider's policies.

Notification permission is optional and supports locally scheduled reminders. Audio playback uses Android media controls and a playback notification. You can revoke permissions in Android Settings; location-based setup or reminders may then be unavailable, while core reading, audio and Tasbih remain usable. Reminder delivery depends on Android and device restrictions.

4. Advertising with Google AdMob

When advertising is enabled in a distributed version, Google AdMob may request and display ads when connectivity is available, subject to consent choices and applicable requirements. Ads are separate from the app's offline content. Network activity can also occur when checking consent or initializing advertising services.

Google's Mobile Ads SDK data disclosure describes automatic collection and sharing of IP addresses (which can indicate general location), app and ad interactions, performance diagnostics, and device or account identifiers, including advertising ID and app set ID where available. These support advertising, measurement and fraud prevention. Actual processing depends on SDK version, permissions, consent, ad mode and optional features. Removing advertising-ID permission does not eliminate all SDK data processing. Additional mediation partners would need separate disclosure.

See Google's Privacy Policy and Google's advertising privacy information.

Current project status (Stage 1): Google Mobile Ads and UMP are connected through an optional runtime. Ads default off; only an explicitly enabled debug build can request an official test banner on About, after Google's consent checks. Live ads and full-screen ads are disabled. Settings exposes Ad privacy choices when UMP requires it and retry controls after failures. The manifest removes advertising-ID, AdServices and install-referrer permissions. Test ads and consent requests can still process data; this is not evidence of a completed production integration or zero SDK traffic.

5. Firebase services

Firebase packages and an optional startup runtime are present. No Android Firebase project configuration was supplied. Firebase defaults off and initializes after the first frame only when explicitly enabled; failures do not block local features. Android's native Firebase provider can initialize when real configuration is included, independently of the Dart enable flag. Inclusion of a package alone does not establish that collection is enabled.

  • Firebase Analytics: Collection, automatic screen reporting, advertising-ID collection and ad-personalization signals are disabled in the manifest. The service also disables Analytics collection when initialized. No custom events, user IDs or user properties are emitted in Stage 1. This draft does not describe Analytics as active.
  • Firebase Crashlytics: Automatic collection is disabled in the manifest and service. No application crash-upload handler was found. This draft does not describe Crashlytics reporting as active.
  • Firebase Remote Config: The optional, disabled-by-default startup service can fetch only the noncritical secondary_banner_enabled flag after initialization. Failure uses a local false value. If enabled, Remote Config uses installation identifiers to deliver configuration; service requests may also involve technical connection data. Disabling Analytics and Crashlytics does not disable Remote Config's own processing.

See Privacy and Security in Firebase.

8. Retention and deletion

Local preferences and progress generally remain until you remove them using available app controls, clear app storage in Android Settings or uninstall the app. Clearing storage removes progress and schedules; the app has no recovery account. Language-pack removal controls apply to installed packs. Android backup and device-transfer rules exclude app data in the inspected project, although manufacturer behavior can vary.

Removing local data does not necessarily remove information already held by Google, an email provider or another service. Provider retention depends on the service and settings. Google documents that Remote Config installation IDs remain until a developer deletion API request, with removal from live and backup systems within 180 days afterward. This applies only if that service is enabled; the inspected app has no dedicated Firebase deletion control. See Firebase retention information.

No app-specific advertising or support retention period has been verified. 9. Security

These measures reduce risk, but no device, storage or transmission method can guarantee absolute security. Protect your device and use supported software.
